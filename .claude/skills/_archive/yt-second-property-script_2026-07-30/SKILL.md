# /yt-second-property-script — Second Property Ladder long-form generator

Topic, project, or news item: `$ARGUMENTS` (or whatever was just discussed).

This is a loop, not a one-off prompt — run all five steps in order every time, reading the referenced files fresh so upgrades to any of them take effect automatically without re-explaining the process.

## 1. Trend + blueprint scan
Check what's actually live in the market right now relevant to `$ARGUMENTS` (real search/trend data, not assumption). Then check it against the current locked Second Property Ladder blueprint — villain, audience, category, mechanism. Use the market angle only where it genuinely maps to the blueprint; don't force a fit, and report if nothing relevant turns up.

**Blueprint source (resolved 2026-07-29):** current doctrine is `01_SOURCE_REFERENCES/The Second Property Ladder x One-Property Trap - FINAL CATEGORY KING HANDOVER BLUEPRINT.docx` (One-Property Trap villain, Know→Move→Own mechanism, DINKS/condo-EC-HDB audience) and `01_SOURCE_REFERENCES/Revenue System x The Second Property Ladder x One-Property Trap.docx` (offer/revenue architecture — ignore its "READY Framework™" naming proposal specifically, superseded by the Handover doc's choice to leave the mechanism unbranded). The earlier "5 Moves™" doctrine is archived in `99_ARCHIVE/` and is not current.

## 2. Real data lookup
Pull verified current facts — developer, land cost/psf, unit count, pricing, timeline for projects; exact thresholds, tiers, and effective dates for policy/regulatory topics. Never invent numbers. Prefer primary sources (government press releases, professional research-house analyses that cite them directly) over secondary blog aggregation, which tends to flatten tiered rules and get thresholds wrong. If Edmund supplies a source document, it is ground truth — cross-check everything else against it, not the reverse. State clearly when official data isn't released yet and use estimates only where explicitly labeled as estimates.

## 3. Build the script
Read `04_YOUTUBE_CONTENT_ENGINE/YouTube_LongForm_Script_Framework_and_Checklist_v1.0.md` in this same campaign folder and apply it in full:
- The core skeleton (promise match → hook/open loop → context bridge → numbered teaching modules → midpoint re-hook → worked example → recap → soft bridge)
- Teach transferable, named, reusable rules in each module — never just information about one example
- Scale depth (§3 of that doc) to justify runtime — 10-12 min for a single-topic video, 15-30 min only where genuine depth (multiple modules, project comparisons, real complexity) supports it. Never pad.
- Thread interactive question beats (§4) — one self-check question per module, one mid-video comment-bait question, one rhetorical question at the midpoint re-hook
- If a real project is featured, weave it through every module per §6, land a nuanced buyer-type verdict, and include the disclosure-line placeholder

## 4. Self-grade
Grade the script against its 5 most relevant criteria (grounding in real data, teaching depth vs. information, blueprint alignment, retention-framework fidelity, disclosure/accuracy where applicable). State one-line critiques for anything short of a 10, and revise before presenting the final version.

## 5. Output
Present the full word-for-word script with framework labels annotated, a timing/word-count table showing how the runtime was derived, and note what topic/project it was built on so a future run on a different topic doesn't need this process re-explained.
